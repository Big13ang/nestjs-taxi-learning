Decorators: code that runs when a class is defined

A decorator is just a function that receives the thing it sits on — a class, a method, a property, or a parameter — and can observe it, change it, or leave metadata on it. It runs once, at definition time, not when you use the thing.

CORE CONCEPTCh 1TypeScript + Nest12 min read

Your note, corrected and sharpened

@Logger()
class Feed {}

const f = new Feed();   // ← Logger does NOT run here

Two small fixes to the raw note: it's class Feed {} — no () after the name — and "runs when you start your project" is true because that's when the file is first imported and the class definition is evaluated. The precise rule is:

Key ideaA decorator runs once, when the class definition is evaluated (module load / app startup in Nest). It does not run on new Feed(), and it does not run per request.
The split that explains NestThe decorator function runs at definition time. What it leaves behind is what acts later: most Nest decorators only store metadata (Reflect.defineMetadata) — e.g. @Get(':id') writes "this method = GET /:id". Nest reads that metadata at startup and at runtime. Definition-time execution, runtime effect.

Mental model

Think of a decorator as a sticker you put on a blueprint, not on the houses built from it. You sticker the blueprint once, while drawing it. Every house built later carries the sticker's effect — but you never re-sticker per house. Heavy work (DB calls, network) does not belong in a decorator for exactly this reason: it would run once, at load, before your app is ready.

All possible decorators — there are exactly 5 kinds

Every decorator in TypeScript (and therefore in Nest) is one of these five. What changes is what it can sit on and what arguments it receives.

KindSits onReceivesYou've seen
1. ClassA classconstructor@Injectable() @Controller() @Module()
2. MethodA methodtarget, key, descriptor@Get() @Post() custom @LogTime()
3. AccessorA get / settarget, key, descriptor — descriptor holds get/setRare in Nest; same shape as method
4. PropertyA fieldtarget, key — no descriptor, return value is ignored@IsString() @Column()
5. ParameterOne argument of a method / constructortarget, key, index@Body() @Param() @Inject() @Req()
Memorize thistarget = the prototype for instance members (Feed.prototype), and the constructor itself for static members and the class. If you can recite the 5 kinds + their arguments, you can read any decorator code — including Nest's source.

Setup note: Nest uses the legacy TypeScript decorator mode, so tsconfig.json needs "experimentalDecorators": true and "emitDecoratorMetadata": true. The Nest CLI scaffold already sets both.

Decorator factory — a decorator that takes arguments

A plain decorator is the function. A factory is a function that returns that function — that's the only way to pass your own values in.

function Logger(prefix: string) {        // 1 · FACTORY — takes YOUR arguments
  return function (target: Function) {   // 2 · the actual DECORATOR
    console.log(`[${prefix}] ${target.name} was defined`);
  };
}

@Logger('FEED')   // call the factory → it returns a decorator → decorator runs on the class
class FeedService {}

// App starts, file is imported → console: [FEED] FeedService was defined
// new FeedService() ten times  → nothing. It already ran, once.
Watch out — the parentheses are the whole difference@Logger = the function itself is the decorator (no arguments possible). @Logger('FEED') = call the factory first, use what it returns. Nearly every Nest decorator is a factory: @Controller('feed'), @Get(':id'), and your future @Roles('ADMIN') in the taxi project is just SetMetadata('roles', ...roles) — a factory.

Multiple decorators — why the order looks reversed

@First()
@Second()
@Third()
class Demo {}

Two different phases, two different directions:

PhaseOrderFor the example
1. Factories are evaluatedTop → bottomFirst() → Second() → Third()
2. Decorators are invokedBottom → topThird → Second → First

Why? It's function composition. @f @g x means f(g(x)) — the decorator closest to the class has to finish first, so the next one up receives its result and can wrap it. Exactly like an onion, or a stack: the last one you put on is the first one that actually applies.

Memory lineFactories read top-down. Decorators run bottom-up. Closest to the class runs first.

And inside one whole class, TypeScript applies things in this fixed order:

  1. Parameter, then method / accessor / property decorators — for each instance member
  2. Same — for each static member
  3. Parameter decorators — for the constructor
  4. Class decorators — last

Examples to memorize — one per kind

Don't memorize all five perfectly today. Memorize example 1 (class + factory) cold, and be able to recognize the shape of the other four.

1 · Class decorator (factory) — tag a class

function Tag(label: string) {
  return function (target: Function) {
    (target as any).label = label;   // leave something on the class itself
  };
}

@Tag('feed-service')
class FeedService {}

console.log((FeedService as any).label);  // 'feed-service' — set at definition time

2 · Method decorator — wrap a method (timing)

function LogTime(target: any, key: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value;
  descriptor.value = async function (...args: any[]) {
    const start = Date.now();
    const result = await original.apply(this, args);
    console.log(`${key} took ${Date.now() - start}ms`);
    return result;
  };
  return descriptor;   // method/accessor decorators may return a new descriptor
}

class FeedService {
  @LogTime
  async getFeed() { /* ... */ }   // decorator runs at definition; the WRAPPER runs per call
}
See the split again

@LogTime itself ran once, at startup, and swapped in a wrapper. The wrapper is what runs on every getFeed() call. That two-step — decorate once, effect per use — is how almost all powerful decorators work.

3 · Property decorator — metadata only

function Required(target: any, key: string) {
  const fields: string[] = Reflect.getMetadata('required', target) ?? [];
  Reflect.defineMetadata('required', [...fields, key], target);
}

class CreateTripDto {
  @Required
  pickup!: string;   // no descriptor exists for properties — metadata is all you get
}

4 · Parameter decorator — mark an argument

function LogParam(target: any, key: string | undefined, index: number) {
  console.log(`Parameter #${index} of ${String(key ?? 'constructor')} is decorated`);
}

class TripsController {
  create(@LogParam dto: object) {}   // prints at definition time: Parameter #0 of create…
}

This is the family Nest's createParamDecorator() builds on — your @CurrentUser() in the taxi project will be one of these, except Nest gives it a factory that also runs per request to extract the value.

5 · Accessor decorator — guard a setter

function Positive(target: any, key: string, descriptor: PropertyDescriptor) {
  const originalSet = descriptor.set!;
  descriptor.set = function (value: number) {
    if (value < 0) throw new Error(`${key} cannot be negative`);
    originalSet.call(this, value);
  };
}

class Wallet {
  @Positive
  set balance(value: number) { /* store it */ }
}

Train on these

Cover the answers, say the output out loud, then check. Predicting output is the fastest way to make the order stick.

Drill 1 — predict the output 
function deco(name: string) {
  console.log(`factory ${name}`);
  return function () { console.log(`decorator ${name}`); };
}

@deco('A')
@deco('B')
class Demo {}

new Demo();
new Demo();
Answer

factory A → factory B → decorator B → decorator A — and then nothing for the two new Demo() calls. Factories top-down, decorators bottom-up, all of it once at definition time.

Drill 2 — spot the bug

A teammate writes a decorator that opens a database connection inside the decorator function "so it's ready before any request." What's wrong?

Answer

The decorator runs at class-definition / module-load time — before Nest has built the app, read config, or connected its own providers. Decorators should be cheap: store metadata or wrap a method. Real connections belong in a provider's lifecycle hook (e.g. onModuleInit — Chapter 2).
