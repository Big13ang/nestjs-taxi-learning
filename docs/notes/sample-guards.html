Guards: the bouncer of your API

A Guard answers one yes/no question before a route runs: is this request allowed in? If it returns false, Nest stops everything and replies 403 — the controller never even hears about it.

SAMPLEConceptAuth5 min

Mental model

Think of a club. The middleware is the street camera — it sees everyone passing. The Guard is the bouncer at the door — it checks your ID and decides. The controller is the party inside — it only meets people who got in.

Key ideaGuards run after middleware and before interceptors, pipes and the controller. They have access to the route's metadata — so they can behave differently per route.

Simple example

Only admins may delete a driver. Instead of checking the role inside every controller, write it once as a Guard:

@Injectable()
export class AdminGuard implements CanActivate {
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    return req.user?.role === 'ADMIN';   // true = in, false = 403
  }
}

@Delete(':id')
@UseGuards(AdminGuard)   // ← bouncer posted at this door
removeDriver(@Param('id') id: string) { /* only admins reach this */ }
See it happen

A driver sends DELETE /drivers/7 → Guard reads role: 'DRIVER' → returns false → 403 Forbidden. The removeDriver method never runs. An admin sends the same request → true → driver deleted.

Common mistake

Watch outDoing role checks inside controllers (if (user.role !== 'ADMIN') throw… copy-pasted everywhere). One forgotten check = one open door. Guards exist so the check lives in exactly one place.

Where you'll use it in the taxi project

InShop / Taxi connectionCh 4 builds DriverGuard and AdminGuard exactly like this — and in InShop, the same pattern is what a throttler / auth guard does at the edge of every route.
